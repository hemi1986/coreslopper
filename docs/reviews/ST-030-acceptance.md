## Edge cases not covered by the story

| Case | Expected by a rule? (cite) | Recommendation |
|---|---|---|
| **A process stops between `saveLibrarySet` and `rm`** (crash, `SIGKILL`, power loss) | **Yes** — the story's Context and `AGG-LibrarySet` invariant "Every file in the entry's folder is named by set.yaml" (`docs/domain/events.yaml:413`). The entry is written without the name first, so the file is left plain and unnamed; `validateLibrarySet` does not see it (`validate-file.ts:283-289`), and scenario 2 makes `set remove` refuse to remove it. The add path already stages copies to avoid the mirror image of this (`library-entry.ts:148-203`). | **fix now** — stage the deletion like the add path stages its copies (rename the file to a hidden staging name in the same folder, write the entry, then unlink; rename back in the catch), so an interruption leaves at most an ignored dot file, never a plain orphan. Add a test that reaches the rollback/durability path (the current tests never reach `set-library.ts:220-223`). |
| Two plate ids share one file through content dedupe (`addLibrarySetFile` with the same bytes under another name) | The invariant "A file is stored once by its content" (`docs/domain/events.yaml:410`) makes one name for both; removing it must remove both plates to keep the folder named. The behaviour is consistent, but only the ref+plate case is tested (`tests/set-library.test.ts:301`), not plate+plate. | question — decide whether removing one file should remove every plate naming it (current) or report which plates share it; the board (ST-032) should show it. |
| A named file is already missing on disk | The invariant "every file it names … exists" (`docs/domain/events.yaml:408`); `rm(..., { force: true })` silently succeeds, so the command prints `✔ … removed` although nothing was deleted. The entry cleanup is a repair, but it is not reported. | question — decide whether to report "the file was already missing"; behaviour is harmless. |
| A plain file in the folder that `set.yaml` does not name (left by hand or by the crash above) | Invariant "every file in the entry's folder is named by set.yaml" (`events.yaml:413`); scenario 2 deliberately refuses it ("a typo never deletes another file"). The command gives the user no way to clean it, and `validate-file` does not flag it. | question — the refusal is per the story; decide whether a reader/doctor check should report the orphan. |
| Concurrent `set remove` and `set add-file` | No locking rule; library writes are atomic but unlocked (G-130, `docs/engineering/conventions.md:80`; already an open question from ST-025 in `docs/stories/OPEN_QUESTIONS.md:18`). A remove racing an add can drop the add's row. | no action — existing workspace-wide gap, not introduced by this story. |
| No `history` row for the removal | `history` is documented as "every later import" (`packages/core/src/schema.ts:1575-1578`), while `EVT-LibrarySetFileRemoved` exists; the board's set page may want removals. | question — record a removal row (and how) or state that history is additions/imports only. |
| Removing the last file leaves a set with no references and no plates | `LibrarySetSchema` allows empty `refs`/`plates` (defaults `[]`), and `addLibrarySet` creates such entries; `set use` then adds an empty set, which is schema-valid. | no action. |
| An unknown set id | `loadLibrarySet` throws `no library set "nope" (<path>)` before any write; verified through the CLI (exit 1). | no action. |
| Path-like, `set.yaml` or dot names | The guard (`basename`, `set.yaml`, leading dot) refuses them; tested at `tests/set-library.test.ts:316`; verified through the CLI. | no action. |
| Reference removal, and a file a reference and a plate both name | Covered by the extra tests at `:287` and `:301`; verified through the CLI. | no action. |
| Production copies | ADR 0052 and the story Context ("Productions that use the set keep their copy"); verified end to end with `set use` then `set remove` — the production file and `sets.yaml` stayed intact. | no action. |
| Long texts, the other language | Removal touches no text field; English only by convention. | no action. |

Verdict: **not accepted** — both scenarios have exact-title tests that really build their Given through the real add seam, enter through `removeLibrarySetFile`, and assert every Then with the scenario's literals; the story tests, the whole set-library file, the full suite and typecheck pass, and traceability, the linter and the CLI are green. The block is the story's own invariant: the command writes the entry without the name first and deletes the file second (`set-library.ts:217-223`), so an interruption leaves a plain, unnamed file in the entry's folder, which `validate-file` does not flag (`validate-file.ts:283-289`) and scenario 2's refusal prevents the command from cleaning. The add path stages its copies for exactly this class of failure (`library-entry.ts:148-203`); the remove path should stage the deletion in the same way and cover the rollback with a test. The remaining rows are questions, not blockers.
