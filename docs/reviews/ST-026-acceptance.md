## Remarks
- The scenario tests enter at `importSets`, the function `set import` calls, which the seam catalog names explicitly ("Set library … `importSets` on a temp workspace"); commander itself is not automated, the same as ST-024, ST-025 and `importCharacters`. I checked the command end to end in `/tmp` workspace roots: a music video with two sets (one without files), `--id` refusal, a missing plate, a re-import with nothing new, `--into`, `--into` with an unknown entry, and `--series` against a canon (`origin: projects/harbor`) — all behave as the story's rules say.
- Scenario 4's *Given* (`the library holds "bar" from "neon-rain"`) is produced by running the SUT once (`importSets(ws, first)`) instead of seeding `library/sets/bar/set.yaml`; it establishes the state, but the *When* is then not the only SUT use in the test (the same style as ST-025's remark).
- Scenario 2 asserts the kept `name` but not the kept `description`/`prompt`. The code never touches them on an existing entry, so this is a coverage gap, not a defect.
- The five tests below the four scenarios (skip/refuse, missing file, path outside the production, `--into`, no bible/unknown set) are the story's rules and the CLI refusals; they carry no `ST-026:` title, which is correct — `check-scenarios.ts` matches exactly the four scenario titles.
- The commit series is one commit per scenario (`1622b1b` … `bbc2be6`) plus wiring (`9a60eb4`) and the seam record (`b19090f`); traceability is by title and `verify.ts`, which are green at HEAD.

## Edge cases not covered by the story
| Case | Expected by a rule? (cite) | Recommendation |
|---|---|---|
| `--into <entry>` on a production with more than one set and no `--id`: every set is merged into the named entry. Verified in a `/tmp` root: `set import neon-rain --into bar` put `roof`'s reference into `bar` while `roof` already had its own entry (`refs: [start.png, start-2.png]`, history row for `from: projects/neon-rain`) | invariant "One set, one entry" (`AGG-LibrarySet`); the story does not say what `--into` means for several sets, and the CLI help says "an earlier copy of the same set" (singular) | question — refuse `--into` unless `--id` names the set, or state the merge behaviour in the story |
| A library plate that has no image (the state the "missing file, not fatal" rule creates) and a later import brings that image: the plate stays fileless and a second plate `<plate>-<slug>` is added, i.e. two plates with the same angle. Verified: `door` (no file) + `door-neon-rain` (`missing-door.png`) | invariant "fills in only what is missing"; the same wording is used for characters and the character code behaves identically (`events.yaml:400` says "the code does this"), so the spec itself is ambiguous | question — either fill the file into the existing plate or say that a plate without an image counts as "another image" |
| A same-id entry that shares a file but has no `library:` link is merged (the middle clause of "one set, one entry"); implemented in `matchSetEntry`, never exercised — only the negative (no shared file → new entry) is a scenario | invariant "… into a same-id entry that shares a file with it" | question — worth one test (the character library's `merges a same-id character that shares a file …` is the precedent) |
| An id plus source slug longer than 80 characters: the `<id>-<slug>`/`<plate>-<slug>` fallback is cut to 80, so the `-2` counter suffix is cut away too; once the 80-character candidate is taken, `matchSetEntry`/`freePlateId` loop without progress (a hang, not an error) | id limit is `MAX_ID = 80` (`library-entry.ts`); reachable only with a very long plate id and project slug, and a second conflicting import | question — cut the stem, not the suffix, or refuse an id that cannot get a free fallback |
| `importSets` copies with `copyByContent` without `stage: true`: if `saveLibrarySet` then fails, the copied files stay unnamed, the folder counts as taken (`idTaken` → `'files'`) and a later `set new` refuses it | invariant "Every file in the entry's folder is named by set.yaml"; `addLibrarySetFile` stages for exactly this reason | question — do the same staging as `addLibrarySetFile` |
| A ref/plate `ref` that is a symlink to a file outside the production passes the `startsWith` check (`resolve`, not `realpath`) and its target is copied in | no story rule; the code treats an outside path as missing (`refuses a set file outside the production`), but a symlink inside the production is not resolved — the same check as the character import | question (rare, same as the character library) |
| A source ref of a non-image type or above 512 MB is copied into the library although `set add-file` refuses it (`LIBRARY_FILE_LIMITS`) | the set bible's refs are not type/size-checked, and `importCharacters` behaves the same; ADR 0052 says the character library's rules hold for sets | question (the rules say nothing; consistent with characters) |
| Name/description/prompt text beyond `addLibrarySet`'s caps (200/4000) is imported as-is; `SetSchema` and `LibrarySetSchema` have no max | `addLibrarySet` caps the fields; the import does not, and neither does `importCharacters` | question |
| Two `set import` runs at the same moment: both load and write `set.yaml`, the second drops the first's additions | library writes are atomic but unlocked — known gap G-130 (`docs/engineering/conventions.md`, "Commands and events") | question (G-130 covers the library, not this story) |
| `--series` on a canon whose `sets.yaml` is missing (references not passed yet) | the story only names the canon as a target; `importSets` refuses with `… has no sets.yaml`, which is clear | question (ST-027 owns the automatic path) |
| The other language | no — English only, no catalog (`docs/engineering/conventions.md`, "UI and texts") | no action |
| The board's Sets view, `set use`, props | out of scope — ST-032, ST-028, ADR 0052 | no action |
