Bug-focused pass over the diff (no findings beyond the table):

- **Unintended effect on public projects:** none. The only way a calendar leaves `others` is `distribution: internal`; `public` and unset both pass `releasedPublicly`, and a public sibling whose `project.yaml` breaks still counts (record 2). `ProjectConfigSchema` strips unknown keys, so a `project.yaml` from a newer runtime does not start failing this read.
- **Read order:** the config read precedes `loadCalendar`, so an internal sibling's calendar is never validated or loaded; a directory removed between `siblingProjects` and the reads just drops out (`readdir`/`existsSync`/`readYamlFile` all degrade to “not there”).
- **Path and identity:** both callers pass `project.paths.root` (`resolve`d in `projectPaths`), so the `dir === projectRoot` skip still matches and the project never reads its own calendar as “other”. Relative or symlinked roots remain the pre-existing weakness, unchanged by this diff.
- **Lock behaviour:** reads only; no lock is taken or needed, and `HS-174`/`otherCalendars` is untouched. The project's own `review/calendar.yaml` is written by `planCalendar` alone (`:118`) — the internal project's file stays as it is, though the new tests do not assert that (structurally safe: only one path is written).
- **`loadCalendar` / `buildCalendar` interaction:** `others` is used for `takenReleases` and the Short `occupied` set only; every kept event of the planning project still comes from `existing`. Dropping a calendar from `others` can therefore only free a day or a slot, never move an event that the project already holds.
- **Cost:** one extra small read per sibling on every plan (N reads → 2N plus the calendar). The board's refresh plans a calendar after a live URL or an approval; on a workspace of dozens of projects this is still trivial, but it is a read per project per plan.
- **Scope:** `schedule.booked` is deliberately untouched (the user's own slot reservations), the internal project's own file is not written, and nothing about ST-041/ST-042 leaked in.

Verdict: **ready to merge** — 0 blockers, 1 major, 4 minors, 1 question. The code change itself is correct and covered for the two internal scenarios; the findings are documentation, a fail-direction choice, one insensitive test and two design/test cleanups.
Most important: the as-is documentation (`docs/architecture.md:191`, the AGG-ReleaseCalendar evidence at `events.yaml:476`, the context map, the **Distribution** glossary entry) still says planning reads every project's calendar — the code and the documented architecture now disagree about the rule this story introduces — and the one test that guards public projects (finding 3) would stay green if the filter skipped public projects instead of internal ones.

## Resolution (main session, 2026-11-24)

- 1 major (documentation): fixed. `docs/architecture.md` names the exception in the planning paragraph and in the internal-project sentence, the AGG-ReleaseCalendar evidence in `docs/domain/events.yaml` and `docs/domain/context-map.as-is.md` now say “every other publicly released project”, and the glossary's **Distribution** entry says an earlier calendar stays on disk and books nothing. ADR 0028 stays as accepted (an accepted ADR is not edited); the rule lives in the CMD-PlanReleaseCalendar rule and the as-is docs.
- 2 minor (fail direction): fixed as recommended. The docblock now states the chosen direction — an unreadable `project.yaml` counts as public and keeps its booking, so a broken file never silently frees a slot — and a test pins it (`counts a sibling whose project.yaml cannot be read as public`). The fail-open choice is deliberate: the collision-safe side, with no rule deciding an unknown distribution.
- 3 minor (insensitive guard): fixed. Scenario 3 asserts `2026-12-11`, the next Friday outside `min_gap_weeks`, so a filter that skips public projects fails too.
- 4 minor (interface): fixed. `CalendarContext.others` in `packages/core/src/calendar.ts` now states the precondition (“the other publicly released projects”).
- 5 minor (duplicated test setup): fixed. ST-036's “plans no release calendar” test uses `siblingCalendar`, which returns the calendar path and its text for the byte comparison.
- 6 question (board): left for the user. The board's calendar of all projects, `/calendar.ics` and `boardProjectDirs` still serve an internal project's earlier calendar; filtering them changes a read model outside CMD-PlanReleaseCalendar. Recorded as an Out of Scope line in the story and a row in `docs/stories/OPEN_QUESTIONS.md`.

Skipped: none. The acceptance remark about the internal project's own file is covered by the same ST-036 byte comparison (the planned project never writes the sibling's calendar).
