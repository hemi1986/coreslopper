## Edge cases not covered by the story

| Case | Expected by a rule? (cite) | Recommendation |
|---|---|---|
| **A process stops during the staged deletion** (between the rename and the save, or between the save and the unlink) | **Fixed** — the file is renamed to a hidden `.removed-*` name before the entry is written, so the story's invariant "Every file in the entry's folder is named by set.yaml" (`docs/domain/events.yaml:413`) holds: the scan treats dot files as staging (`library-entry.ts:155-166`), and the add path uses the same convention. The failed-move path is tested at `tests/set-library.test.ts:354`; the save-failure rename-back branch (`set-library.ts:233`) is not tested. The rename→save window still leaves the entry naming a missing file until the save — the code review explicitly accepts this as the add path's trade (`saveLibrarySet` → `commitCopies`). | no action (blocker resolved); optionally cover the save-failure rollback, which cannot be induced portably without mocking the filesystem |
| A failed unlink of the hidden staging file after the entry is written | The entry is consistent and the hidden file is ignored by the scan, but the command throws after the successful write, so the CLI reports an error; a `.removed-*` file stays behind. No rule violated. | question — minor: report or log the leftover, or accept it as a staging artefact |
| Two plate ids share one stored image (content dedupe) | Invariant "A file is stored once by its content" (`docs/domain/events.yaml:410`); removing the one file removes both plates to keep the folder named. Now tested at `tests/set-library.test.ts:316` and stated in the docblock. | no action — decided and covered |
| A named file is already missing on disk | Invariant "every file it names … exists" (`docs/domain/events.yaml:408`); the command repairs the entry, and the docblock now says so.
