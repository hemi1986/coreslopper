The LinkedIn media check uses the same filtered list. `release` warns about every other `data.shorts` entry. The `publish` fallback filters the same way. The new test covers a leftover cut-Short entry.
- **#3: fixed.** `runCalendar` takes the one Short from the manifest's placed `shorts/<slug>-9x16.mp4`, only if that file is still on disk. `release` keeps an earlier copy under the same condition (`unchanged`). The new test shows both commands plan the same events, with none before the vertical version is placed.
- **#4: fixed for the asset checks** (`Shorts`/`Short thumbnails` are N/A). The upload-text part is still open, see R2-2.
- **#5: still open.** It was not acted on. It stays a question for the developer (no change in evidence). `release-facts.ts:145` now combines the manifest's shape with today's length, so the board's plan can disagree with the folder after a cut across 3 minutes. That is the same gap.
- **#6: fixed.** One core `releaseForm` returns the shape and the Shorts source, and `release`, `qa`, `release-qa`, the calendar and `publish` all read it. `release-facts` uses `shortsSourceOf` with the manifest's shape, which is justified. `status.ts:37` still uses `releaseShape` alone. That is fine, because it only lists files.
- **#7: fixed.** `wholeEpisode` is now the marker that QA reads.
