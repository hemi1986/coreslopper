Strong in-process 01

Give the release one plan

Files

  • packages/cli/src/release.ts
  • packages/core/src/release.ts
  • packages/cli/src/release-texts.ts
  • packages/cli/src/release-qa.ts
  • packages/cli/src/release-board-data.ts
  • packages/cli/src/publish.ts
  • packages/cli/src/release-autopilot.ts

Problem

No module states what one post of one release contains; five consumers rebuild files, text and limits from raw upload data and have already drifted — the TikTok Short is checked with one caption and sent with another.

Solution

One release plan turns the project, the upload data and the channel into each post’s files, exact text and limits in effect; the folder writer, checks, board, autopilot and uploader read it, and the manifest and board fields become projections.

Wins

  • →One text: shown, checked, sent
  • →Limits resolved once
  • →Leverage: one plan, five consumers
  • →Caption drift fails a test
  • →Locality: post rules in one module
  • →Manifest and board become projections
Strong in-process 02

Collapse the two library lifecycles

Files

  • packages/cli/src/library-entry.ts
  • packages/cli/src/character-library.ts
  • packages/cli/src/set-library.ts
  • packages/cli/src/board/characters.js
  • packages/cli/src/board/sets.js
  • packages/cli/src/release-board.ts
  • tests/set-library.test.ts · character-library.test.ts

Problem

Characters and sets are one Library context in ADR 0052 but two full lifecycles in code: six parallel functions, two board views, three route blocks and three test suites pin the copies.

Solution

Grow the entry seam into the one lifecycle for characters and sets, with the entry file, file roles, target key and words as data inside it; the sound library stays its own context.

Wins

  • →One lifecycle, two kinds
  • →Delete one of two full twins
  • →Library views stop importing each other
  • →Leverage: a new kind is data
  • →Tests stop cloning
  • →Locality: entry rules in one module

Already decided. ADR 0052 calls characters and sets one Library context; this closes the gap between the decision and the code.

Strong in-process 03

Give the release records one owner

Files

  • packages/cli/src/release-calendar.ts
  • packages/cli/src/release-autopilot.ts
  • packages/cli/src/autopilot-state.ts
  • packages/cli/src/publish.ts
  • packages/cli/src/board-production.ts
  • packages/cli/src/board/release.js
  • packages/core/src/autopilot.ts

Problem

The release status, autopilot log, publish log and lock are written through four modules with two approval rules, so a stale approval can read as released and checklist ticks move when a row appears.

Solution

One release-records module owns the status, the logs and the lock; approval, take-over, done rows and checklist keys are entries it names, and calendar planning becomes a client.

Wins

  • →One approval rule
  • →One lock, one write path
  • →Checklist keys stop moving
  • →Stale approvals read as stale
  • →Leverage: four callers, one owner
  • →Locality: record shape in one module

Already decided. ADR 0046 (proposed) decided four records, each with its lock; the code still has two approval rules and one unvalidated write.

Strong in-process 04

Lift release facts out of the board view

Files

  • packages/cli/src/release-autopilot.ts
  • packages/cli/src/release-board-data.ts
  • packages/cli/src/release-board.ts
  • packages/cli/src/publish.ts
  • packages/cli/src/board/app.js
  • packages/cli/src/board-production.ts

Problem

The posting runner builds the board’s whole view to learn a few facts, imports the board’s shell module, and reloads an approved project five times per round even when nothing is due.

Solution

One release-facts module owns project, identity, upload data, manifest files, calendar, status, settings and workspace root; the board view and the runner both build on it, and project discovery leaves the board shell.

Wins

  • →Break the runner ↔ board cycle
  • →Five loads per project become one
  • →Runner tests stop using the board view
  • →Root stops being derived as ../..
  • →One song.json reader
  • →Leverage: two consumers, one read
Strong in-process 05

Make the uncommitted series budget one rule

Files

  • packages/cli/src/series.ts
  • packages/cli/src/new-project.ts
  • packages/cli/src/generate.ts
  • packages/core/src/cost.ts
  • packages/core/src/state.ts
  • packages/cli/src/board-wizard.ts
  • tests/series-budget.test.ts

Problem

Uncommitted Series Budget is series total minus canon spend minus episode budgets in the wizard and board, but a canon batch checks only the series state’s remaining budget, which ignores committed episodes.

Solution

Move the uncommitted-series-budget rule into the core budget rule and have episode creation and every canon batch read the same amount.

Wins

  • →One meaning of remaining
  • →Canon cannot spend committed money
  • →Pure rule, inline table test
  • →Wizard and batch agree
  • →Leverage: one check, both entry points
  • →Locality: the rule sits in core
Strong in-process 06

Close the generation ledger’s side doors

Files

  • packages/cli/src/index.ts
  • packages/cli/src/generate.ts
  • packages/core/src/state.ts
  • packages/cli/src/qa.ts
  • tests/generation-characterization.test.ts
  • tests/qa-manifest.test.ts

Problem

runBatch carries the invariant that manifest cost equals recorded spend, but estimate re-derives the price and spend raises spend without a manifest line, so the invariant holds only if callers avoid two commands.

Solution

Quote through the generation module’s existing price resolution, and make manual spend a manifest-backed ledger write through it or remove the command.

Wins

  • →One price rule
  • →Ledger invariant always true
  • →Two side doors closed
  • →Estimate sees the remaining budget
  • →Leverage: every quote from one path
  • →Locality: the ledger has one owner
Worth exploring ports & adapters 07

Put never twice behind one seam

Files

  • packages/providers/src/http.ts
  • packages/providers/src/publish/http.ts
  • packages/providers/src/publish/tiktok.ts
  • packages/providers/src/publish/youtube.ts
  • packages/providers/src/publish/x.ts
  • packages/providers/src/publish/linkedin.ts
  • packages/providers/src/publish/instagram.ts
  • packages/cli/src/release-autopilot.ts

Problem

The rule that a public post is never sent twice is decided at each call site: two retry stacks, three definitions of “may have gone out”, and a poll loop per adapter — twice in TikTok.

Solution

One failure-classification seam — fatal, retryable, uncertain — and one poll-until-terminal helper; adapters say when the last byte left, and the runner, publish and the pinned-comment step share the class.

Wins

  • →One “uncertain” rule
  • →One retry budget
  • →One poll loop
  • →Never twice, tested once
  • →Adapters declare; the runner decides
  • →Leverage: every platform call crosses it

Already decided. ADR 0046 decided never twice on every platform; the code still classifies uncertainty three ways.

Worth exploring in-process 08

Let each board view own its routes

Files

  • packages/cli/src/release-board.ts
  • packages/cli/src/board/release.js
  • packages/cli/src/board/app.js
  • packages/cli/src/board/wizard.js
  • packages/cli/src/board/characters.js
  • packages/cli/src/board/sets.js

Problem

The board shell validates and interprets release records itself, re-lists the workspace on every status click, and serves view documents, while the release view’s module has no routes.

Solution

A release-view route function beside the wizard and library ones owns the view’s records and bodies; the shell keeps only the write guard, the static page, whitelisted media and dispatch.

Wins

  • →Shell shrinks to a host
  • →Release rules leave the shell
  • →One route seam per view
  • →No workspace scan per click
  • →Page helpers become testable
  • →Locality: a view changes in its module

Already decided. ADR 0049 decided a view’s routes live in that view’s module; production, review, release and autopilot are still inline.

Top recommendation

01 · Give the release one plan

It is the missing deep module under the release hot spot: one definition of each post’s files, text and limits means what the board shows, QA checks and the uploader sends can no longer disagree — and the records and facts deepenings land more cleanly once that definition exists.
