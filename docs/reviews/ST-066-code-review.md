# Code review – ST-066: A wizard adds a library sound and sets its cue while it plays
Base: marathon/2026-11-28-2 · Commits: 3 · Date: 2026-11-28

Security pass (requested): no finding. All server and user data reaches the DOM through `el()` (`textContent`,
`createTextNode`, `setAttribute`); the only `innerHTML` is the empty-string reset in `main()`. The upload query
parameters and the `/api/sounds/<id>` and `/sound-files/<id>` paths are `encodeURIComponent`-encoded; the server
re-checks the id (`checkId`), sanitises the file name (`safeName`), caps the size (`UPLOAD_LIMITS.audio`), converts with
ffmpeg under `-protocol_whitelist file` and refuses a non-audio file (`not-audio`). The `accept` attribute is only a
picker hint, which is correct since the server decides. Writes go through `trustedWrite` (origin check) as before. The
server-side parsing of cue and trim (`seconds`, `parseTrim`, `librarySoundTimeProblems`) is unchanged and refuses
negative, non-finite or out-of-range values, so no client input can get around the invariant "a cue and a trim lie
inside the sound's length, and a cue inside the trim".

Cue/trim arithmetic: **Set cue here** stores `currentTime − trim start field` and **Trim start here** shifts a set cue
by `old start − new start`. Both match the rule that the cue counts from the trim start, and they match the detail page
(`sounds.js:340`). The gap is in deciding whether the cue was "left untouched" (finding 1).
