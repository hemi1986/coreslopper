Where the rule lives: the CMD-RunAutopilotRound rule (“A round leaves a project with distribution internal alone … its plan lists no event of it”) is enforced by two guards on `releasedPublicly(context.project.config)`, one in `runProject` (`release-autopilot.ts:224-228`) and one in `autopilotOverview` (`:533-536`). The round's guard sits before `approvalHolds`, the plan, the pending-upload polling, the due events, the pinned comment and the microsite step, so nothing of the project can post in a round — also with an approval from before it became internal, which is exactly scenario 1's premise. The round still writes `.cache/release-run.last`; that is the round's own record (AGG-AutopilotRound invariant), not the project's, so it is the right thing to keep. `releasedPublicly` is the existing core predicate already used by `release`, `release-calendar`, `status`, `qa`, `board-production` and `release-board`, so no new cross-module edge and no second definition of “internal”.

Bug-focused pass over the diff (no findings beyond the table):

- **Scope of the guard:** the early return precedes every action of the round, so a held approval, a due event, an upload to poll, the pinned comment and the microsite step are all skipped; a dry run prints the same line and posts nothing (consistent with “a dry run takes no lock and writes nothing”).
- **Public projects unchanged:** the predicate is false only for `distribution: internal`; unset and `public` both pass, and scenario 3 plus the older round tests stay green.
- **Board:** the release tab is hidden when `hasRelease` is false (`release-board-data.ts:735`, `board/lib.js:191-198`), so the plan the board computes for an internal project is not reachable from the UI; the remaining board readers of an earlier calendar are covered by the ST-040 open question and ST-042.
- **Board write routes:** `retryEvent`/the board's autopilot POST (`release-board.ts`) do not consult `distribution`, so a crafted trusted board request could append to an internal project's autopilot log; the round would not act on it and the tab is hidden, so this is inert — worth knowing, not this story.
- **Read cost:** `projectReleaseContext` still loads for an internal project before the guard (one full read per project per round, read-only). Correct, only wasteful; it also means a broken `project.yaml` of an internal project still reports “skipped (…)”, not the internal line.
- **Time and locks:** no `new Date()` added (the overview's `options.now ?? new Date()` is pre-existing); `AutopilotDeps.now` still supplies the round's clock; no new lock, no new write.
- **Scope:** nothing of ST-042 (approval refused) leaked in; ST-036's `release`/`qa` behaviour untouched. `docs/stories/BACKLOG.md` and the story's `status: in-progress` are bookkeeping, `depends_on: [ST-036]` is done.

Verdict: **ready to merge** — 0 blockers, 1 major, 5 minors.
Most important: the written rule and the code now disagree in five places — the glossary's **Distribution**, `docs/architecture.md`, `docs/publishing.md`, the shipped `workspace/AGENTS.md` and `RM-AutopilotPlan` all still describe an autopilot that posts every approved release, so a user or agent reading them cannot know that an internal project's earlier approval posts nothing.
