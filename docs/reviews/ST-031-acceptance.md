## Remarks (conventions, minor)

- **`ui: true` on a story without a UI deliverable.** The frontmatter sets `ui: true`, but the story's own Context defers the board's set page to ST-032 and neither scenario has a screen. The flag is harmless for acceptance but misleading metadata (it triggers the UX utility for no UI work). Optionally set `ui: false` and keep `ui: true` on ST-032.
- **Two domain commands share the CLI verb `set remove`.** `CMD-RemoveLibrarySetFile` (`--file`) and `CMD-DeleteLibrarySet` (no `--file`) both wire `set remove <id>`; the model itself defines it that way (`docs/domain/events.yaml:2000-2011`, `ST-030`'s `--file`), so this is not a deviation, only worth knowing when reading the help.
- **The CLI deletes without a confirmation.** The command description in the model mentions "after a confirmation that names where the set is used"; the story's Context limits that confirmation to the board. The CLI mirrors `character remove` (unconditional), so this is consistent with the story, but a destructive command with no "used in" warning is a question for the user, not a scenario failure.
- **`docs/stories/BACKLOG.md` is modified but uncommitted** in the worktree (`In Progress: 1`, ST-031 moved out of Ready) while `git diff main...HEAD` does not contain it. If the branch is merged as-is, the generated backlog is stale until the next hook run. Commit the regenerated file with the story (it will change again when `/implement` sets `done`).
- **Scenario 1 builds the "used" production directly** with the `production` helper (`sets.yaml` + files) instead of `createProject` + `useSet`. That matches `RM-SetLibrary`'s definition of "used in" exactly and is the helper the ST-026 tests use, but it does not exercise `loadProject` on the surviving production. A stronger Given would create a real music video and use the set; not required by this story.

## Edge cases not covered by the story

| Case | Expected by a rule? (cite) | Recommendation: fix now / question |
|---|---|---|
| **Broken `set.yaml`** (hand edit or invalid YAML) in the folder | The aggregate invariant "every file in the entry's folder is named by `set.yaml`" is already violated; deleting the folder repairs it. Implemented and tested at `tests/set-library.test.ts:401`. | no action — covered and deliberate |
| **Leftover folder with no `set.yaml`** (interrupted write) | Same invariant; the command removes it (tested at `:412`) rather than refusing. Read literally, scenario 2 says "the library has no set 'garage'" → refused, yet a folder without an entry is also "no set". The code comment states the decision ("the folder's presence decides, not its `set.yaml`"). | question — keep repair-by-delete, or refuse a folder that holds no entry and send the user to a repair command? Not a blocker: the scenario's Given is a clean library, and removing an invariant-violating folder is defensible |
| **A set used by a series canon and, indirectly, by its episode** | Episodes take their bibles from the canon ("An episode's bibles are the canon's", `docs/engineering/conventions.md`); deleting the library entry touches neither the canon's nor the episode's copy. The board's "used in" (ST-032) must count the canon, not the episode. | no action here — belongs to ST-032; state it in the read model |
| **Invalid id** (`../bar`, `/etc`, spaces, uppercase, over 80 chars) | The id is the folder name; a path-like id would escape `library/sets`. `checkLibraryId` refuses before any filesystem access (tested at `:423`; the >80-char branch shares the guard). | no action |
| **Failed unlink of the staged `.removing-<uuid>` folder** | No rule violated: the entry left the library, the command throws and tells the user the relative path to delete by hand. Not tested (mirrors the ST-030 untested rollback). | question — minor; optionally test with a mocked `rm` |
| **A stale `.removing-*` folder after a crash** | Hidden and inert to `idTaken` (dot names are skipped), but a future Sets view must skip dot directories when listing (none exists yet; ST-032). | question — make ST-032's listing skip dot entries |
| **Concurrent `set remove` / `set add-file` / `set use`** | Library writes are atomic but unlocked (G-130, `docs/engineering/conventions.md`); a delete racing an add can drop the add's row. Existing workspace-wide gap, not introduced here. | question — existing G-130 gap |
| **Empty `library/sets` after the last deletion** | Scenario 1 only says the library has no set; leaving the empty root is correct and the test asserts `readdir` `[]`. | no action |
| **Long texts, other language** | Deletion touches no text field; English only by convention. | no action |
