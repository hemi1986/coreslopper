Bug pass over the rest of the diff. No defects found:

- **Scenarios:** all four tests carry the exact `ST-004: …` title and assert their "Then" through
  `checkSoundLibrary`, `loadLibrarySound` and `listLibrarySounds` – the remeasured length/hash, the reported
  folder that stays out of `list`, the cue message with the entry untouched, the missing file. Expected values are
  independent literals (2.0 s, the file's own hash), not recomputed the way the code does.
- **Write-only-in-a-valid-state:** the write at 418 goes through `LibrarySoundSchema.parse` after
  `librarySoundTimeProblems` against the *new* length (401-412), so a shorter swapped file can never be written
  with an out-of-range cue or trim. Skipping the write when the time problems are non-empty is correct: the stored
  entry stays internally valid and the next check reports again.
- **Broken yaml:** `readYamlFile` wraps read, parse and schema failures in `ValidationError`
  (`packages/core/src/project.ts:140-157`); the load branch catches everything and reports it as `invalid`, so a
  hand-broken entry does not abort. The id-not-the-folder-name branch is reached only for entries the schema
  accepts (it is not redundant with `loadLibrarySound`, which does not compare the id).
- **Nothing is created or removed:** the only write is to an existing entry's `sound.yaml`; no `mkdir`, no `rm`,
  no rename, so the story's "not added" and Out of Scope hold for folders and loose files.
- **`addLibrarySound` unchanged:** apart from the `length > 0` guard (finding 10) the call order and formulas are
  identical (measure → time problems → hash/original hash → duplicate → loudness → parse → write → rename), and the
  ST-001/ST-002 tests stay green. The silent refusal still happens after the duplicate lookup, as before.
- **Seam:** `checkSoundLibrary(root)` on a temp workspace is the seam catalog's "Command" row; no new seam, nothing
  to confirm with the user.
- **Process note:** `e0ad1b4` adds all six tests at once but only the missing-file branch; the folder, swapped and
  cue tests stay red over two later commits. That is horizontal slicing rather than one tracer bullet at a time
  (tdd skill). Not a code defect – the tests themselves are sound – but it is why the duplicate and corrupt-file
  edges were never designed against.

Verdict: fix blockers first
Most important finding: #1 – a corrupt or unreadable `sound.wav` makes `sound check` exit 1 with `✖ Could not read the duration …`, reporting nothing and leaving earlier entries rewritten; the command built to survive hand-edited media must report that entry as `invalid` instead.
